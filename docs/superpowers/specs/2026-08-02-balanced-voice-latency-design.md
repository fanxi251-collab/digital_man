# 均衡模式语音识别与响应提速设计

当前时间：2026-08-02（Asia/Shanghai）

## 目标

在保留景区专名纠错、句尾保护和低置信度人工确认的前提下，缩短游客松开录音按钮后到完成转写、开始检索以及模型输出首字的等待时间。

本次优化只覆盖现有数字人实时语音问答链路，不改变文字问答、WebSocket 公开事件、前端消息结构、数字人音频播放格式或景区路线面板契约。

## 当前链路与问题

现有链路为：

1. 浏览器 AudioWorklet 将麦克风音频转换成 16kHz、16 位、单声道 PCM，并按约 100ms 上传。
2. 游客松开按钮后，浏览器继续固定采集 300ms，保护句尾语音，然后发送 `audio.commit`。
3. 实时语音模型完成转写并返回完整文本。
4. 后端先执行词库归一化，再无条件调用问题理解模型，在候选中选择纠正文本并生成扩展问题。
5. Agent 使用 `lite` 配置收集证据，随后实时模型生成文字或数字人口播。

主要可控延迟来自固定 300ms 句尾等待，以及清晰、无需纠错的语音仍会增加一次问题理解模型往返。100ms 上传分片还会让实时转写的输入可见性最多滞后一帧。

## 方案选择

采用均衡模式，不启用基于未完成转写的推测式预检索。

推测式预检索虽然可能进一步降低检索等待，但会在实时转写变化时产生无效请求，并可能让错误问题与证据短暂绑定。当前目标优先降低确定性等待和冗余调用，避免扩大系统复杂度与证据错配风险。

## 前端音频采集设计

### 低延迟分片

AudioWorklet 的目标格式保持 16kHz、16 位、单声道 PCM，将单块时长从约 100ms 调整为约 60ms。较小分片可以更早向上游提供语音，同时仍保持足够的数据块大小，避免改成过碎的逐帧传输。

质量统计不再假设固定 100ms。每个采集块携带实际样本数或由样本数计算的时长，`voicedDurationMs` 按真实块时长累计。这样调整分片不会错误改变“至少 300ms 有效语音”的提交门槛。

### 自适应句尾保护

松开按钮时根据最近采集块是否仍包含有效声音选择等待时长：

- 最近音频已低于静音阈值：等待 160ms。
- 最近音频仍达到有效声音阈值：等待 240ms。
- 缺少可靠指标或指标异常：使用 240ms 安全值。

等待期间继续采集和上传，保留句尾辅音与景区名称。再次录音、取消回答或连接中断时，必须取消尚未触发的提交任务。

有效语音不足 300ms、持续严重削波或没有上传成功的音频块时，继续拒绝提交，并给出原有可操作提示。

## 后端转写纠错设计

确定性词库归一化先于可选模型调用，输出保持 `TranscriptCorrection` 契约。根据结果分流：

- `none`：没有发现需要纠正的景区专名，直接接受上游转写。
- `high`：精确别名或唯一高置信度候选，直接接受词库纠正。
- `medium`：存在合理但不完全确定的候选，调用问题理解模型结合会话上下文选择。
- `low`：调用问题理解模型帮助整理候选，但最终仍要求游客确认。

只有 `medium`、`low` 或存在多个有效候选时才允许调用问题理解模型。模型异常时回退到确定性结果，不向游客暴露内部异常。低置信度的确认事件与编辑确认流程保持不变。

快速路径返回空扩展问题列表，由既有会话上下文规则和 `lite` 证据检索继续处理问题；不得为了补回扩展问题重新增加模型调用。

## 回答链路与可观测性

现有 `lite` 证据收集、回答契约、证据注入和数字人简短口播继续保留。此次不新增推测检索，也不改变模型或对外接口。

为每轮语音在后端内部日志记录以下相对耗时，日志只包含 trace/turn 标识、阶段名和毫秒数，不记录原始音频：

- `audio_committed_to_transcript_ms`
- `transcript_normalization_ms`
- `evidence_prepare_ms`
- `response_request_ms`
- `response_first_delta_ms`

前端只负责缩短提交前等待；后端日志负责区分语音服务、纠错、检索和生成的耗时。若某阶段没有完成，不伪造数值。

## 组件边界

- `pcm-capture-worklet.js`：只负责重采样、PCM 分片和每块音频指标。
- `audioCaptureQuality.js`：只负责真实时长累计、质量判定与自适应句尾等待策略。
- `usePcmAudio.js`：管理浏览器音频资源并把块指标交给质量跟踪器。
- `useRealtimeChat.js`：管理一轮录音生命周期，并使用策略结果安排 `audio.commit`。
- `realtime/conversation.py`：执行确定性纠错快速路径和疑难候选模型分流。
- `realtime/session.py`：维护实时事件顺序并记录阶段耗时。

以上模块通过现有数据结构通信，不新增前端依赖，单个文件继续控制在 800 行以内。

## 异常与兼容性

- 无音频指标、非有限时长或未知质量：使用 240ms 句尾保护，不提前提交。
- 纠错模型超时或异常：使用词库确定性结果；低置信度仍进入人工确认。
- WebSocket 断线、取消或新一轮录音：取消旧的句尾计时器，禁止提交陈旧 turn。
- 音频服务错误：保持当前工具错误和文字输入降级，不猜测转写。
- 所有现有客户端事件名和载荷字段保持兼容；新增耗时仅进入内部日志。

## 测试策略

按 TDD 实施，每项生产行为先写失败测试并确认失败原因：

1. 前端单元测试验证 60ms 实际时长累计不改变 300ms 有效语音门槛。
2. 前端单元测试验证静音句尾选择 160ms、仍在发声或异常指标选择 240ms，并验证取消不提交。
3. 前端契约测试验证 AudioWorklet 使用约 60ms 分片并携带块时长。
4. 后端单元测试验证 `none` 和唯一 `high` 走快速路径，问题理解模型调用次数为零。
5. 后端单元测试验证 `medium`、`low` 和多候选仍调用问题理解模型，异常时安全回退。
6. 实时会话测试验证事件顺序、低置信度确认和纠错后文本注入不回归。
7. 运行前端完整测试与生产构建、相关后端测试以及后端全量测试。

## 验收标准

- 浏览器固定 300ms 句尾等待替换为 160–240ms 自适应等待。
- 采集分片从约 100ms 降至约 60ms，质量时长仍按真实音频计算。
- 清晰且无需纠错的语音不调用问题理解模型。
- 高置信度词库纠错不调用问题理解模型；中低置信度保护机制保持有效。
- WebSocket、消息、数字人播放、来源与路线面板对外契约不变。
- 前端测试、前端生产构建、相关后端测试和后端全量测试通过。
- 内部日志可以区分提交后转写、纠错、证据准备和首个输出阶段耗时。

## 不在本次范围

- 更换实时语音供应商或模型。
- 使用浏览器原生 SpeechRecognition 替换现有上游服务。
- 根据未完成转写进行推测式证据检索。
- 调整文字问答的答案篇幅或证据规划。
- 新增前端视觉组件或第三方音频依赖。
