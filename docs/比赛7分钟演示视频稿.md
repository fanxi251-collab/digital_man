# “灵境智导”比赛七分钟演示视频稿

当前时间：2026-07-20 12:47:00 +08:00（Asia/Shanghai）

适用版本：当前比赛 Docker 镜像 `lingjing-ai:competition`

## 一、录制目标

建议成片控制在 **6 分 45 秒至 6 分 55 秒**，为片头、页面加载或平台转码预留余量。整段演示围绕两条主线展开：

1. 游客从“咨询—探索—路线—美食—反馈”完成完整游览决策。
2. 管理人员从“数据洞察—内容维护—反馈处理”完成运营闭环。

口播语速建议保持每分钟 220—240 个汉字。页面等待时不要沉默，可继续讲解当前功能的价值。

## 二、录制前准备

### 1. 启动并检查系统

```powershell
docker load -i ".\lingjing-ai-competition-amd64.tar"
docker run --name lingjing-ai-demo --env-file ".\competition.env" -p 8000:8000 -d lingjing-ai:competition
docker ps
```

浏览器预先打开并确认以下页面能够访问：

- 游客端：`http://localhost:8000/visitor/guide`
- 管理端：`http://localhost:8000/admin/analytics`

### 2. 浏览器和录屏设置

- 使用 1920×1080 分辨率，浏览器缩放设为 90% 或 100%。
- 关闭书签栏、下载提示、通知弹窗和无关标签页。
- 提前授权麦克风和网页音频，避免数字人演示时临时弹窗。
- 预先加载一次游客端和管理端，让图片、Live2D 和图表进入缓存。
- 保留两个浏览器标签页：第一个游客端，第二个管理端，减少现场输入网址的时间。
- 录制时使用全屏窗口，鼠标移动要慢，点击后停留 1—2 秒供评委看清变化。

### 3. 演示问题

主问题建议提前复制到剪贴板：

> 我第一次来灵山胜境，和老人、孩子一起游玩，只有三个小时，请推荐一条轻松的路线，并介绍沿途重点景点。

数字人补充问题：

> 灵山大佛最值得了解的文化特色是什么？

如果现场模型响应较慢，可在录制前先完成一次主问题，录制时通过“历史会话”打开已有回答，同时说明系统支持会话持久化。

## 三、七分钟正式演示稿

### 00:00—00:30　开场与项目定位

**画面操作**

从游客端开场页开始，等待品牌动画结束，停留在“AI 智能导游”主界面。

**口播**

> 各位评委老师好，我们的项目是“灵境智导”，一套面向灵山胜境的智能游览与运营服务平台。它不是单一的景区问答机器人，而是把智能导游、数字人讲解、景点探索、地图路线、美食推荐、游客反馈和管理分析连接起来，为游客提供行前、行中到游后的一站式服务，也为景区提供持续更新和运营决策能力。

### 00:30—01:50　AI 智能导游与数字人

**画面操作**

1. 在输入框粘贴主问题并发送。
2. 回答生成时，缓慢展示对话区；回答完成后向下浏览结论、重点景点、路线建议和引用来源。
3. 点击“历史会话”，展示会话保存能力后关闭抽屉。
4. 切换到“数字人模式”，选择一个数字人形象，输入或按住语音按钮询问补充问题。

**口播**

> 首先演示核心的 AI 智能导游。我输入一个真实的复合需求：第一次到访、同行有老人和孩子、游玩时间只有三个小时。系统不会只做关键词匹配，而是由智能体识别人物、时间和路线约束，调用景区知识库与路线工具，再组织成面向游客的答案。可以看到，回答先给出明确建议，再列出沿途重点和游览注意事项，并保留资料来源，降低大模型凭空生成的风险。
>
> 系统还会按照匿名游客标识保存历史会话，游客无需注册，也能继续上一次咨询。切换到数字人模式后，可以选择不同形象，通过文字或麦克风提问。后端先检索可靠证据，再生成适合口播的简洁答案；实时音频同时驱动 Live2D 口型和状态变化，让传统图文导览变成更自然的交互讲解。

### 01:50—02:35　景点探索

**画面操作**

1. 点击左侧“景点探索”。
2. 展示推荐景点和全部景点数量。
3. 在搜索框输入“大佛”或选择一个分类。
4. 打开“灵山大佛”详情抽屉，展示图片、简介、开放信息和建议游览时长。
5. 如详情页有“问问智能导游”入口，点击后立即返回，不再等待第二次回答。

**口播**

> 对不确定目的地的游客，景点探索页提供了更直观的图文发现方式。游客可以按名称、特色和分类筛选景点，点击卡片后查看详细介绍、开放信息、标签和建议停留时间。结构化景点数据由管理端维护，发布后会直接同步到游客端。景点详情还可以继续跳转到智能导游提问，实现“先浏览、再追问”的连续体验。

### 02:35—03:30　互动地图与路线规划

**画面操作**

1. 点击“互动地图”。
2. 依次切换“全部、景点、美食”图层。
3. 选择一个起点和终点，选择“步行”，点击“开始规划”。
4. 展示地图线路、距离、预计时间和关键步骤。

**口播**

> 在互动地图中，景点和美食被统一成可规划的地点。游客可以切换图层、查看地点详情，并选择起点、终点以及步行或驾车方式。系统通过高德地图能力返回真实的距离、预计时长和路线步骤；如果地图组件暂时不可用，文字路线仍然可以正常显示。这种降级设计保证了弱网或外部服务波动时，核心信息依旧可用。

### 03:30—04:10　美食推荐

**画面操作**

1. 点击“美食推荐”。
2. 展示编辑精选区域。
3. 依次选择“景区内”“素食友好”或一个预算等级。
4. 打开一张美食卡片，展示招牌菜、预算、地址和营业信息。

**口播**

> 游览服务不仅包括看什么，也包括在哪里吃。美食页同时覆盖景区内和周边推荐，可按范围、类别、口味、预算和素食需求组合筛选。详情中提供招牌菜、消费等级、地址和营业信息，游客还可以把感兴趣的美食带到地图页继续规划，形成景点与餐饮联动的行程。

### 04:10—04:45　游客反馈闭环

**画面操作**

1. 点击“游客反馈”。
2. 快速展示星级、反馈类型、内容和可选联系方式。
3. 不必现场提交新数据，向下展示“我的反馈进度”及已有反馈状态。

**口播**

> 游览结束后，游客可以匿名提交评分和分类反馈，联系方式完全可选。系统会生成反馈编号，并让当前浏览器持续查看待处理、处理中和已解决状态，以及管理员的公开回复。这样，游客意见不再停留在一次性表单，而是进入可以跟踪的服务处理流程。

### 04:45—05:50　管理后台与运营闭环

**画面操作**

1. 切换到预先打开的管理端“游客分析”标签页。
2. 缓慢滚动核心指标、年度趋势、游客画像、排行榜、消费和满意度图表。
3. 点击“知识库资料”，展示资料列表和上传入口。
4. 点击“景点资料”或“美食推荐”，展示结构化编辑表单。
5. 点击“游客反馈”，选择一条反馈，展示状态与管理员回复区域。

**口播**

> 接下来是管理端。游客分析看板把年度数据转化为客流趋势、游客画像、景点偏好、消费结构、满意度和运营洞察，帮助管理人员快速识别高峰月份、重点客群与待改善项目。
>
> 内容维护采用两类数据：知识库资料支持文本和 Markdown 上传、解析、分块与重新索引，为 AI 回答持续补充可靠知识；景点和美食则采用结构化管理，可以维护坐标、图片、营业信息、发布状态与推荐标签。游客端刚才看到的内容都来自这里。反馈管理页支持筛选问题、更新处理状态并填写回复，回复会回到游客端，从而完成“发现问题、处理问题、告知游客”的运营闭环。

### 05:50—06:35　技术架构与可靠性

**画面操作**

切换到一张预先准备的架构图；如果没有架构图，则停留在管理端，并在画面角落叠加以下关键词：`Vue 3 / FastAPI / LangGraph / RAG / Qdrant / WebSocket / Docker`。

**口播**

> 技术上，前端使用 Vue 3 构建游客端，后端使用 FastAPI 提供接口和静态资源。LangGraph 负责智能体流程编排，RAG 基于本地 Qdrant 检索景区资料，可选知识图谱进一步补充关系信息；天气、地点和路线由高德工具提供，数字人通过 WebSocket 完成实时文本、音频和口型同步。系统对外部服务设置了降级策略：模型不可用时仍可进行本地检索，地图不可用时保留文字路线，Redis 和知识图谱也都是可选增强。

### 06:35—07:00　Docker 交付与结束语

**画面操作**

显示终端中的 `docker ps`，突出容器状态为 `healthy`；随后回到游客端首页或项目标题页结束。

**口播**

> 为方便比赛部署，我们已将前后端、运行依赖、静态资源以及演示数据制作成 Linux AMD64 Docker 镜像。镜像使用非 root 用户运行，带有健康检查，可以离线导入并一条命令启动。以上就是“灵境智导”：用可信的智能导游改善游客体验，用可维护的数据和运营闭环服务景区管理。感谢各位评委老师观看。

## 四、录制时的关键动作清单

按顺序只完成以下动作，避免临场遗漏：

1. 游客端发送一次复合问题。
2. 展示回答来源和历史会话。
3. 切换一次数字人模式。
4. 景点页搜索并打开一次详情。
5. 地图页规划一次步行路线。
6. 美食页设置筛选并打开一次详情。
7. 反馈页展示提交表单和处理进度。
8. 管理端展示分析图表、知识库、结构化内容和反馈处理。
9. 最后展示 Docker 容器 `healthy` 状态。

## 五、超时和故障应急

### 超过七分钟时优先删减

1. 删除景点页的搜索动作，只打开一张卡片，可节省约 10 秒。
2. 美食页只展示筛选，不打开详情，可节省约 10 秒。
3. 管理端只展示游客分析、知识库和反馈三页，可节省约 15 秒。
4. 技术架构段压缩到 25 秒，可再节省约 20 秒。

不要删减开场定位、AI 智能导游、管理闭环和结束语，这四部分最能体现项目完整性。

### 模型响应较慢

- 打开预先生成的历史会话，并口播：“系统已保存本次咨询，我们直接查看生成结果。”
- 不要在成片中长时间展示加载动画，等待超过 5 秒即可剪掉中间等待部分。

### 数字人没有声音

- 保留数字人形象、字幕与状态变化，口播：“在无音频环境下，系统会自动保留文字回答。”
- 不要反复点击麦克风或刷新页面，以免打乱后续时间轴。

### 高德地图没有绘制

- 展示地点列表、距离、耗时和文字步骤，并说明系统具有地图失败降级能力。

## 六、字幕与剪辑建议

- 片头字幕：`灵境智导｜景区智能游览与运营服务平台`
- 核心能力字幕：`可信问答｜数字人交互｜路线规划｜内容运营｜数据洞察`
- 技术字幕：`Vue 3 + FastAPI + LangGraph + RAG + Qdrant + WebSocket`
- 结尾字幕：`让每一次游览更从容，让每一条反馈有回应`
- 页面加载超过 3—5 秒的部分可以直接跳剪，但操作前后画面各保留约 1 秒。
- 背景音乐音量保持在人声音量的 10%—15%，数字人播报时进一步降低。
- 不要在画面中展示 API Key、`.env` 内容、管理员联系方式或真实个人信息。
